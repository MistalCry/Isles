# ADR-0004：数据访问与迁移方案（MySQL + MyBatis-Plus + Flyway）

## 状态

已采纳（Accepted）· 2026-11-14 · 数据库由项目负责人选定 MySQL + Redis

## 背景

平台核心数据为账号、频道、成员关系、内容与消息，关系明确、需要事务与复杂查询（动态流、成员列表、消息历史）。需要确定数据库、数据访问层与版本化迁移方案，并保证长期可维护、可回滚、可审计。

约束：

- 负责人选定 MySQL + Redis。
- 本机 MySQL 8.0.45 已运行；单机部署，Docker Compose 生产环境。
- 单人维护，需要低认知负担 + 明确迁移历史。

## 候选方案

### 方案 A：MyBatis-Plus + Flyway（采纳）

- 优点：
  - MyBatis-Plus 提供 CRUD、分页、逻辑删除、条件构造器，减少样板代码。
  - 复杂查询可直接写 SQL，可控性强，适合动态流/统计类查询。
  - Flyway 迁移只追加、有版本历史，符合规范 §8。
- 缺点：
  - SQL 分散在 XML/注解中，需评审防注入与 N+1。
  - 相比 JPA，缺少实体关系导航，需手工维护关联查询。

### 方案 B：Spring Data JPA + Flyway

- 优点：领域建模友好、派生查询方便、社区标准。
- 缺点：复杂查询易退化为 N+1 或难以表达；社交动态流类查询常需原生 SQL，JPA 优势打折。

### 方案 C：MyBatis 原生 + Flyway

- 优点：SQL 完全可控。
- 缺点：CRUD 样板代码多，开发效率低。

## 决策

采纳**方案 A**：

- 数据库：MySQL 8.0，库名 `my_social_channel`，字符集 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci`。
- 数据访问：MyBatis-Plus 3.5.18（`mybatis-plus-spring-boot4-starter`），分页插件统一分页参数，逻辑删除字段 `deleted_at`。
- 迁移：Flyway，脚本位于 `backend/src/main/resources/db/migration/`，命名 `V{n}__{描述}.sql`，只追加不回改；破坏性变更两阶段（加列/双写 → 回填 → 切读 → 删列）。
- 连接池：HikariCP（Boot 默认），连接串显式 `serverTimezone=UTC`、`useUnicode=true&characterEncoding=utf8`。
- Redis：缓存/令牌/限流，后续 Pub/Sub；不存放业务主数据。
- 测试：单元测试用 Mockito；仓储/集成测试连接本机 `my_social_channel_test` 库，`@Transactional` 回滚保证可重复。

## 后果

### 正面

- CRUD 开发快，复杂查询仍可写 SQL 优化。
- 迁移历史清晰，支持前向兼容与回滚演练。
- MySQL 8 + Redis 8 本机与生产（Docker）一致，环境差异小。

### 负面 / 成本

- 需要约束 SQL 质量：禁止拼接 SQL、列表查询必须分页、关注索引与执行计划。
- 逻辑删除需注意唯一索引冲突（应用层配合或冗余列）。
- 集成测试依赖本机 MySQL，CI 需提供 MySQL 服务（GitHub Actions service 或等价方案）。

### 风险与缓解

- 风险：Flyway 与 MySQL 8 版本兼容 → 缓解：使用 Boot 管理的 Flyway + `flyway-mysql` 模块，首次迁移即验证。
- 风险：开发库与生产库字符集/时区不一致 → 缓解：迁移脚本显式声明字符集/时区，部署清单检查。
