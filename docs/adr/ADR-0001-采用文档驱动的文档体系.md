# ADR-0001：采用文档驱动与分层文档体系

## 状态

已采纳（Accepted）· 2026-11-14

## 背景

本项目是一个长期演进的社交频道平台，处于规划期。在编码开始前，需要解决三个问题：

1. 多人（含 AI 代理）协作时，规范与约定如何落地，而不是靠口头传达；
2. 重大技术决策（技术栈、数据模型、实时通信方案）如何留下可追溯的依据；
3. 需求、架构、接口、数据库等信息如何避免散落、过期和互相矛盾。

若等到开发中后期再补文档体系，成本高且容易流于形式。

## 候选方案

### 方案 A：不建立正式文档，仅用 README + 口头约定

- 优点：启动最快，无维护成本。
- 缺点：决策不可追溯；新人/AI 代理需要反复确认；长期必然出现信息不一致。

### 方案 B：使用外部 Wiki / 在线文档平台

- 优点：编辑体验好，便于非技术成员阅读。
- 缺点：与代码分离，容易过期；评审与变更不跟代码同 PR；AI 代理难以稳定读取。

### 方案 C：文档即代码（Docs as Code）+ 分层文档体系 + ADR

- 优点：与代码同仓库、同 PR、同评审、可 diff、可追溯；AI 代理可直接读取；分层明确、职责清晰。
- 缺点：需要纪律（DoD 检查），否则文档会滞后。

## 决策

采用**方案 C**：

1. 在 `docs/` 下建立分层文档体系（L0 入口 → L1 治理 → L2 决策与架构 → L3 需求与契约 → L4 交付与运行 → L5 归档），规则见 `docs/01-文档体系与维护规范.md`。
2. 工程规范以 `docs/00-工程开发规范.md` 为唯一事实来源，所有代码、流程、AI 协作均受其约束。
3. 重大技术决策使用 ADR 记录：一决策一文件、编号递增不复用，索引维护在 `docs/adr/README.md`。
4. 文档更新纳入 PR 的完成定义（DoD），与代码同 PR 更新。
5. 文档、规范、ADR 全部纳入 Git 版本管理，随代码一起评审与发布。

## 后果

### 正面

- 决策与规范可追溯：任何"为什么这样做"都能在仓库中找到依据。
- 需求 → 架构 → 契约 → 代码 有明确链路，减少返工。
- AI 代理可在每次任务开始时读取稳定上下文，降低跑偏风险。
- 新成员或新会话可快速恢复项目上下文。

### 负面 / 成本

- 每次变更需要同步文档，短期增加工作量。
- 需要定期巡检（双周/季度）防止文档过期。

### 缓解

- 用模板降低写作成本（`docs/templates/`）。
- 用更新触发矩阵（STD-01 §5）明确"什么时候必须更新哪份"，避免全量重写。
- DoD 清单 + 双周巡检 + 季度全量评审，把过期当作缺陷处理。
