# ADR-0003：实时通信方案（STOMP over WebSocket）

## 状态

已采纳（Accepted）· 2026-11-14

## 背景

平台需要频道内实时消息推送与在线事件。负责人最初倾向 Socket.IO，但后端已确定为 Spring Boot（Socket.IO 主要面向 Node.js 生态）。负责人最终授权技术侧按 Spring 最佳实践决定。

约束：

- 后端 Spring Boot 4.1；前端 Vue 3。
- 需要连接鉴权、心跳、断线重连、频道订阅、后续多实例扩展。
- 单人维护，避免引入社区维护度低的协议兼容层。

## 候选方案

### 方案 A：Spring WebSocket + STOMP（采纳）

- 优点：
  - Spring 官方支持（`spring-boot-starter-websocket` + `@EnableWebSocketMessageBroker`），与 Spring Security 过滤器链集成顺畅。
  - STOMP 提供订阅/目的地模型，天然适配"频道订阅"。
  - 前端 `@stomp/stompjs` 成熟，重连、心跳、订阅管理开箱可用。
  - 后续多实例可通过 Redis Pub/Sub 桥接广播。
- 缺点：
  - 非 Socket.IO 协议，不能直接复用 Socket.IO 客户端。
  - 简单 broker 不持久化消息，需应用层保证（先落库再推送）。
  - 不支持 SockJS 时对极老浏览器不友好（现代浏览器无影响）。

### 方案 B：netty-socketio（保留 Socket.IO 协议）

- 优点：前端可继续使用 socket.io-client，API 熟悉。
- 缺点：Java 端社区库，需自行保证与 Socket.IO 各版本协议兼容；Spring Boot 4 适配风险高；出问题排查成本高。

### 方案 C：原生 WebSocket + 自定义 JSON 协议

- 优点：完全可控、无协议层依赖。
- 缺点：心跳、重连、订阅、鉴权、背压全部自研，与单人维护目标冲突。

### 方案 D：SSE / 轮询

- 优点：实现简单。
- 缺点：无法满足双向低延迟消息；轮询浪费资源且实时性差。

## 决策

采纳**方案 A：Spring WebSocket + STOMP**，设计要点：

1. 端点 `/ws`，原生 WebSocket（不启用 SockJS）。
2. STOMP `CONNECT` 帧携带 `Authorization: Bearer <accessToken>`，`ChannelInterceptor` 校验并绑定 Principal；订阅 `/topic/channels/{channelId}` 前校验成员身份。
3. **写路径走 REST**：消息先持久化（含频道内 `seq`），成功后由服务端广播；客户端断线重连后按游标补拉，保证不丢消息。
4. 心跳双端 10s；前端重连采用指数退避 + 抖动，重连后重新订阅。
5. 多实例扩展：v1 单实例；水平扩展时接入 Redis Pub/Sub 桥接，前端不变。

## 后果

### 正面

- 与 Spring Boot 技术栈一致，减少第三方兼容层风险。
- 订阅模型与频道业务天然对应，代码量小。
- 安全集成简单（复用 JWT 校验逻辑）。

### 负面 / 成本

- 前端不能使用 socket.io-client，需引入 `@stomp/stompjs`。
- 需要应用层保证消息顺序与补拉（已通过 `seq` + REST 历史接口解决）。

### 风险与缓解

- 风险：单实例重启导致连接中断 → 缓解：前端自动重连 + 游标补拉。
- 风险：广播性能瓶颈 → 缓解：v1 规模可控，后续接 Redis Pub/Sub 与多实例。
