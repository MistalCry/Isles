# 文档体系与维护规范

> 目的：让文档**可发现、可信任、可维护**。文档不是一次性产物，而是随代码持续演进的工程资产。
> 本文档回答四个问题：需要维护哪些文档？每份文档什么时候必须更新？谁负责？如何评审与归档？

## 1. 基本原则

1. **单一事实来源（SSOT）**：同一信息只在一个地方维护，其他地方用链接引用，禁止复制粘贴。
2. **文档即代码**：文档与代码同仓库、同 PR 评审；文档变更同样走 PR 与版本管理。
3. **文档分层**：按读者与用途分层，入口文档轻，细节文档深；每份文档只有一个主题。
4. **谁改代码谁更新文档**：变更的发起者负责同步相关文档，评审者负责检查。
5. **可执行性**：流程类文档必须包含清单、模板或命令，避免只写"要重视"。
6. **过期即缺陷**：与代码不一致的文档等同于缺陷，需按缺陷流程修复。

## 2. 文档分层与目录

### 2.1 分层模型

| 层级 | 定位 | 读者 | 文档 |
| --- | --- | --- | --- |
| L0 项目入口 | 一分钟了解项目与状态 | 所有人 | `README.md`、`CHANGELOG.md`、`CONTRIBUTING.md` |
| L1 工程治理 | 怎么干活、要遵守什么 | 全部开发者 | `docs/00`、`docs/01` |
| L2 决策与架构 | 为什么这样设计、系统长什么样 | 开发者 / 评审者 | `docs/02-架构设计.md`、`docs/adr/` |
| L3 需求与契约 | 做什么、接口与数据长什么样 | 产品 / 开发 / 测试 | `docs/03`–`docs/07` |
| L4 交付与运行 | 怎么测、怎么部署、怎么排障 | 开发 / 运维 | `docs/08`–`docs/10`、发布记录 |
| L5 历史 | 历史决策与归档 | 需要追溯的人 | `docs/archive/` |

## 3. 文档元信息与格式规范

### 3.1 必须包含的 Front Matter

除 `README.md`、`CHANGELOG.md` 外，所有文档必须以 YAML Front Matter 开头：

```yaml
---
id: STD-00               # 文档编号，全局唯一
title: 工程开发规范       # 标题
version: 0.1.0           # 文档版本（SemVer；内容级变更升 PATCH，结构调整升 MINOR，重写升 MAJOR）
status: draft            # draft | review | approved | superseded | archived
owner: lead              # 负责人（成员变更时转移）
last_updated: 2026-11-14 # 内容最后变更日期
reviewers: []            # 最近一次评审人
related: [STD-01]        # 关联文档 ID
---
```

- `status` 流转见 §4；`last_updated` 与 Git 提交日期必须一致。
- 文档标题（`#` 一级标题）与 `title` 一致。

### 3.2 编号与命名

| 类型 | 命名规则 | 示例 |
| --- | --- | --- |
| 固定文档 | `NN-中文主题.md`，NN 为两位数、全局唯一、不复用 | `05-API设计.md` |
| ADR | `ADR-NNNN-kebab-case-标题.md`，NNNN 从 0001 递增 | `ADR-0002-采用-postgresql.md` |
| 模板 | 中文名 + 模板 | `templates/技术设计模板.md` |
| 归档 | `archive/YYYY/<原文件名>` | `archive/2026/03-需求规格-v1.md` |
| 发布记录 | `archive/releases/YYYY-MM-DD-vX.Y.Z.md` | — |

- 编号一经分配永不复用；被废弃的编号在索引中标注 `superseded`，不删除文件。
- 文件名避免空格与特殊字符；中文文件名允许，但链接需正确转义。

### 3.3 写作要求

- 每份文档开头写清 **目的 + 读者 + 范围**，让读者 10 秒内判断是否该继续读。
- 结论先行：先给结论/决策，再给背景与推导。
- 使用清单、表格、代码块提升可执行性；避免大段无结构文字。
- 命令与配置必须可直接复制执行；路径使用仓库相对路径。
- 图表使用 Mermaid（渲染友好、可 diff）；图片放 `docs/assets/`（如采用）。
- 禁止"待补充"长期存在：新文档允许 `TBD`，但必须有截止时间或关联 issue。

## 4. 文档生命周期

```
创建(draft) → 评审(review) → 批准(approved) → 维护(approved，持续更新) → 废弃(superseded/archived)
```

| 状态 | 含义 | 进入条件 |
| --- | --- | --- |
| `draft` | 草案，内容可能大改 | 新建文档 |
| `review` | 待评审 | 作者认为可评审 |
| `approved` | 已批准，作为依据 | 评审通过 |
| `superseded` | 被新版本/新决策替代 | 有替代文档，标注指向 |
| `archived` | 归档，不再维护 | 项目阶段结束或内容过时 |

- 架构、需求、API、数据库、安全类文档**必须达到 `approved`** 才能作为开发依据。
- `superseded` / `archived` 文档移到 `docs/archive/`，保留历史，不删除。

## 5. 更新触发矩阵（何时必须更新哪份文档）

| 变更内容 | 必须更新 | 说明 |
| --- | --- | --- |
| 新增 / 修改 / 废弃 API | `05-API设计.md` + OpenAPI 契约 + `CHANGELOG.md` | 契约先行 |
| 表结构 / 索引 / 迁移 | `06-数据库设计.md` + 迁移说明 + `CHANGELOG.md` | 标注发布顺序与回滚方式 |
| 架构调整 / 技术选型 / 模块边界 | `02-架构设计.md` + 新 ADR | 重大决策一决策一 ADR |
| 需求新增 / 变更 / 删除 | `03-需求规格.md` + `10-路线图与里程碑.md` | 变更需记录影响面 |
| 领域术语新增 / 改名 | `04-领域模型与词汇表.md` + 全仓库代码命名 | 保证术语一致 |
| 认证 / 授权 / 权限矩阵变化 | `07-安全与合规.md` + 相关测试 | 权限必须有测试覆盖 |
| 测试体系 / 覆盖目标 / E2E 场景变化 | `08-测试策略.md` | — |
| 环境 / 部署 / 告警 / 回滚方式变化 | `09-部署与运维.md` + 发布清单 | — |
| 发布 | `CHANGELOG.md` + 发布记录 | 每次发布必做 |
| 工程规范调整 | `00` / `01` + `CHANGELOG.md` | 规范版本号递增 |
| P0 / P1 缺陷复盘 | 复盘文档（`docs/archive/incidents/`） | 记录根因与改进项 |
| 里程碑调整 | `10-路线图与里程碑.md` | 说明调整原因 |

> 判断口径：**任何会改变"外部可见行为、协作方式或运维动作"的变更都必须更新文档。**

## 6. 完成定义（DoD 的文档部分）

任何 PR 合并前必须确认：

- [ ] 本次变更涉及的上表文档已更新，或已确认不涉及
- [ ] 新增文档已登记到 `docs/README.md` 与本文档清单表
- [ ] 文档中的链接有效（相对路径、锚点可跳转）
- [ ] 图表、代码块、命令可读可执行
- [ ] 若为重大决策：ADR 已创建并关联 PR
- [ ] `last_updated` 与版本号已更新（如适用）

## 7. ADR（架构决策记录）机制

- **何时写**：技术选型、架构风格、数据存储、通信协议、第三方服务、破坏性变更、有争议的权衡。
- **不写什么**：可逆的小决策、纯实现细节、已有规范覆盖的内容。
- **编号**：`ADR-NNNN` 递增，永不复用。
- **结构**：背景（问题与约束）→ 候选方案（≥ 2 个，含"不做"）→ 决策 → 后果（正面/负面/风险）→ 关联。
- **不可修改**：已批准的 ADR 只允许追加"补充说明"；被替代时新建 ADR 并在旧 ADR 标注 `Superseded by ADR-XXXX`。
- **索引**：`docs/adr/README.md` 维护全部 ADR 的列表与状态。

模板见 [ADR 模板](templates/ADR模板.md)。

## 8. 评审与维护节奏

| 节奏 | 动作 | 负责人 |
| --- | --- | --- |
| 每次 PR | 按 §6 检查文档 | 作者 + 评审者 |
| 每迭代 | 更新需求状态、里程碑、CHANGELOG | lead |
| 每两周 | 文档巡检：`last_updated` 与代码变更对比，标记过期 | lead |
| 每月 | 架构/API/DB 文档与实现一致性抽查 | lead |
| 每季度 | 全量文档评审：删除失效内容、合并重复、修订规范 | lead |
| 每次重大决策 | 写 ADR 并登记索引 | 决策提出者 |

- 文档评审与代码评审同等对待：`blocking` 级问题（如文档与实现矛盾）必须修复。
- 评审记录可附在 PR 评论中；文档 `reviewers` 字段记录最近评审人。

## 9. 归档规则

- 触发：文档被替代、所属功能下线、项目阶段结束。
- 动作：移至 `docs/archive/YYYY/`，保留原文，在文档头部标注 `status: archived` 与归档原因/日期。
- 归档文档不参与日常维护，但不得删除（历史可追溯）。
- 归档记录在 `docs/README.md` 的"归档"分区中索引。

## 10. 文档质量度量

| 指标 | 目标 | 检查方式 |
| --- | --- | --- |
| 关键文档就绪率 | 开发启动前 L2/L3 文档 100% 到位 | 清单表核对 |
| 文档新鲜度 | 关键文档 `last_updated` 距今 ≤ 90 天（无相关代码变更时除外） | 双周巡检 |
| 链接有效率 | 100% 相对链接可跳转 | 巡检脚本 / 人工抽查 |
| ADR 覆盖 | 所有重大决策均有 ADR | 季度评审 |
| 模板使用率 | 新文档优先使用模板 | 评审检查 |
