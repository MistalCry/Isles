# 工程开发规范

> 本规范约束本项目的**全部代码、文档、配置与发布流程**。规范中的强制项（【必须】）是合并卡点；
> 例外必须在 PR 中说明理由并经项目负责人批准。本规范随项目演进持续修订，修订需走 PR 并更新版本号。

## 1. 总则

### 1.1 基本原则

1. **正确性优先**：可读性 > 简洁性 > 性能。先做对，再做快，最后做美。
2. **显式优于隐式**：配置、依赖、错误类型、数据契约尽量显式，拒绝"魔法"。
3. **小步快跑**：提交小、PR 小、发布小；任何一步都可以安全回滚。
4. **自动化守门**：能交给工具的不依赖自觉 —— 格式化、Lint、类型检查、测试、安全扫描全部进 CI。
5. **安全默认**：默认拒绝、最小权限、不信任输入、密钥不入库。
6. **文档即代码**：文档与代码同仓库、同 PR 更新；重大决策必须留下 ADR。
7. **可观测优先于猜测**：日志、指标、追踪是排障的一等公民，不是事后补丁。

### 1.2 约束级别

| 级别 | 含义 | 违反后果 |
| --- | --- | --- |
| 【必须】 | 强制要求 | 阻塞合并；确需例外须负责人批准并记录 |
| 【应当】 | 默认遵守 | 允许有理由的例外，PR 中说明 |
| 【建议】 | 最佳实践 | 无强制力，评审时提示 |

## 2. 技术栈与工程结构

> 【架构确认后细化】本章在架构决策落定（见 `docs/02-架构设计.md` 与 ADR）后补全具体版本与目录。

### 2.1 技术栈清单（待填）

| 层 | 选型 | 版本 | 说明 |
| --- | --- | --- | --- |
| 前端 | 待定 | — | — |
| 后端 | 待定 | — | — |
| 数据库 | 待定 | — | — |
| 缓存 / 队列 | 待定 | — | — |
| 实时通信 | 待定 | — | — |
| 部署 | 待定 | — | — |

### 2.2 目录结构原则

- **按业务领域组织**（feature / domain 优先），而非按技术类型横向切分。
- **依赖单向**：接口层 → 应用层 → 领域层 → 基础设施层；禁止反向依赖与循环依赖。
- **模块自治**：每个模块可独立测试、独立理解；跨模块调用走显式接口。
- **共享代码克制**：共享代码进 `shared/` 前需评审，防止其演变为"无处安放代码的垃圾桶"。
- 架构确认后，目录结构必须写入 `docs/02-架构设计.md`，变更需同步文档并评审。

### 2.3 命名约定（通用）

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 代码目录 / 文件 | kebab-case（框架约定优先） | `channel-member/`、`use-channel.ts` |
| 类 / 类型 / 组件 | PascalCase | `ChannelMember`、`MessageList` |
| 变量 / 函数 | camelCase | `resolveChannel()` |
| 常量 | UPPER_SNAKE_CASE | `MAX_MESSAGE_LENGTH` |
| 数据库表 | snake_case 复数 | `channel_members` |
| 数据库列 | snake_case | `created_at` |
| API 路径 | kebab-case 复数名词 | `/api/v1/channels/{channelId}/members` |
| 环境变量 | UPPER_SNAKE_CASE | `DATABASE_URL` |
| 领域事件 | `聚合.过去式动作` | `channel.member_joined` |
| 测试文件 | 与被测文件同名 + `.test` / `.spec` | `channel.service.test.ts` |

- 布尔值命名以 `is` / `has` / `can` / `should` 开头。
- 禁止拼音、禁止中英文混拼；业务术语与 `docs/04-领域模型与词汇表.md` 保持一致。
- 缩写词按整体读音规则：`userId`（非 `userID`）、`httpUrl`；类名 `UserDTO`、`ApiClient`。

## 3. 编码规范

### 3.1 通用【必须】

- 统一格式化工具 + 提交前钩子；禁止手工对齐代码风格。
- Lint、类型检查、静态分析零错误；**新代码零新增警告**。
- 禁止提交：注释掉的代码、调试输出、未使用的依赖、无主 TODO。
- 所有外部输入必须校验（schema 校验），禁止信任客户端。
- 禁止吞异常：捕获后必须处理、包装并保留原始 cause，或显式记录后抛出。
- 错误信息双通道：面向用户可读（i18n key）+ 面向日志可诊断（稳定错误码 + 上下文）。
- 时间统一 **UTC 存储**、API 使用 ISO 8601、展示层按用户时区；禁止本地时间入库。
- 分页查询必须有上限；禁止无界查询与全表扫描。
- 写操作考虑幂等：唯一约束、幂等键或去重表。
- 单文件超过 500 行【应当】拆分；函数超过 50 行【应当】拆分。
- 禁止魔法值：数字、颜色、阈值、超时时间统一进常量或配置。

### 3.2 后端

- 分层职责单一：控制器/路由只做参数校验与编排；业务逻辑在应用/领域层；数据访问在仓储层。
- 一个用例一个事务边界；明确事务隔离级别；禁止长事务。
- 事务内禁止网络调用（发消息、调第三方）；需要时使用 Outbox / 领域事件异步化。
- 禁止 N+1 查询；列表查询必须验证执行计划或 EXPLAIN。
- 敏感操作写审计日志：谁、何时、对什么资源、结果如何。
- 后台任务 / 定时任务必须幂等、可重试、有超时与死信处理。
- 对外接口不暴露内部实现细节（异常栈、表结构、内部 ID 语义）。
- 并发写共享资源需显式加锁或乐观锁，并在代码注释中说明策略。

### 3.3 前端

- 展示与逻辑分离：数据获取、业务逻辑抽入 hooks / service；组件只负责渲染。
- 状态管理：局部状态优先；全局状态只放跨页面共享的状态；服务端数据交给查询缓存库，不复制进全局 store。
- 样式统一方案（CSS Modules / Tailwind / 设计系统）；颜色、间距、字号走 **Design Token**，禁止散落魔法值。
- 可访问性：语义化标签、键盘可达、可见焦点、颜色对比度达标、图片有 `alt`、必要时 `aria`。
- 国际化：用户可见文案一律走 i18n key，禁止硬编码文案。
- 性能：路由级代码分割、图片懒加载 + 响应式尺寸、长列表虚拟化（> 100 项）、避免不必要的重渲染。
- 每种数据视图必须实现 **加载 / 空 / 错误** 三态；页面级错误边界不可省略。
- 表单必须做客户端校验 + 服务端校验（前端校验只为体验，不代替服务端）。

### 3.4 注释与文档

- 注释解释"**为什么**"，不解释"是什么"（代码本身应能说明是什么）。
- 导出的公共 API、非直观算法、兼容性 hack 必须有文档注释。
- TODO 格式：`// TODO(#123): 原因与计划`；禁止无主 TODO。
- 复杂正则、位运算、时区处理、并发假设必须注释。
- 新增/修改对外行为（API、配置、命令行、事件）必须同步更新文档。

## 4. Git 工作流与提交规范

### 4.1 分支模型

- 采用**主干开发**：`main` 始终可发布；功能在短生命周期分支上开发。
- 分支命名：`feat/<issue>-<slug>`、`fix/<issue>-<slug>`、`chore/<slug>`、`docs/<slug>`、`refactor/<slug>`。
- 分支生命周期【应当】≤ 3 天，超长分支必须拆小或说明原因。
- `main` 受保护：禁止直接 push；必须 PR + CI 全绿 + 评审通过。
- 单一维护者时，仍须走 PR 并完成自查清单，保留可追溯记录。

### 4.2 提交信息（Conventional Commits）

```
<type>(<scope>): <subject>

<body: 为什么改、影响面、取舍>

<footer: BREAKING CHANGE / Refs #123>
```

- `type`：`feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert`
- `type` 与 `scope` 使用英文小写；`subject` 使用中文描述，统一风格，祈使句，≤ 72 字符。
- 一个提交只做一件事：格式化与逻辑修改**分开提交**；大重构与功能开发**分开提交**。
- 破坏性变更必须在 footer 标注 `BREAKING CHANGE:` 并说明迁移方式。

示例：

```
feat(channel): 支持频道成员分页查询

成员列表在频道规模增长后一次返回不可用，改为游标分页，默认 20 条，上限 100 条。

Refs #42
```

### 4.3 Pull Request

- PR 标题遵循提交规范；描述必须包含：变更内容 / 关联需求 / 验证方式 / 影响面 / 文档更新 / 界面截图（如有 UI）。
- 有效改动【应当】≤ 400 行；超出必须拆分。
- 合并方式：**Squash Merge**，保持主干线性历史；合并前先 rebase 到最新 `main`。
- 禁止 force push 已被评审的分支（除非先说明并重新评审）。
- PR 模板中的检查清单必须逐项确认，不允许全部勾选而实际未验证。

## 5. 代码评审

### 5.1 评审关注点（Reviewer 清单）

- [ ] 需求覆盖：正常路径 + 边界 + 异常路径是否都处理
- [ ] 安全：鉴权、越权（IDOR）、注入、XSS、敏感信息泄露
- [ ] 数据：迁移、索引、事务边界、并发、兼容性
- [ ] 错误处理：异常是否被正确捕获、记录与呈现
- [ ] 测试：新增分支是否有测试，测试是否真的能失败
- [ ] 文档：文档、CHANGELOG、ADR 是否同步
- [ ] 可维护性：命名、结构、重复代码、复杂度

### 5.2 评审规则

- 评审时效【应当】≤ 1 个工作日；作者对每条意见必须响应（修改或说明理由）。
- 使用约定化标签：`nit:`（可选）、`suggestion:`（建议）、`question:`（疑问）、`blocking:`（阻塞）。
- 对事不对人；评论指代码，不指作者。
- `blocking` 必须解决后才能合并；`nit` 可协商。
- 评审通过不等于测试通过：CI 是独立门禁。

## 6. 测试策略

### 6.1 测试分层

| 层级 | 占比目标 | 范围 | 特点 |
| --- | --- | --- | --- |
| 单元测试 | ~70% | 纯函数、领域逻辑、校验规则 | 快、无外部依赖 |
| 集成测试 | ~20% | API、数据库、仓储、消息 | 用容器化依赖，可重复 |
| 端到端测试 | ~10% | 关键用户旅程 | 少而精，覆盖主链路 |

> 覆盖率门禁：核心业务域 ≥ 85%，整体 ≥ 70%（架构确认后校准）。新增代码覆盖率不得低于基线。

### 6.2 必须覆盖的场景

- 权限矩阵（每种角色 × 每个操作）
- 输入校验（空值、超长、非法类型、越界）
- 幂等与并发（重复提交、竞态、乐观锁失败重试）
- 分页边界（空页、最后一页、游标失效）
- 时间与时区（跨天、夏令时如适用）
- 失败路径（超时、依赖不可用、重试与降级）
- 安全相关逻辑（越权访问、内容净化）

### 6.3 测试规范

- 命名：`should_<期望>_when_<条件>` 或 `given_<前置>_when_<动作>_then_<结果>`。
- 测试独立、可重复、无执行顺序依赖；每个测试自建数据、自清理。
- 外部依赖使用测试替身；集成/E2E 使用容器化依赖，禁止依赖共享环境。
- 禁止 flaky 测试：发现即修复或隔离并登记 issue；**禁止用重试掩盖不稳定性**。
- 缺陷修复必须先写复现测试（回归测试），再修复，最后确认测试由红转绿。
- 契约测试：前后端、服务之间的接口用 OpenAPI 契约验证。

## 7. API 设计规范

- 风格：REST + JSON（若架构决议采用 GraphQL/RPC，则以对应规范补充，但本文的兼容性、错误码、分页原则不变）。
- 版本化：对外路径 `/api/v1/...`；破坏性变更升版本，不原地改语义。
- 资源命名：复数名词、小写、连字符；嵌套 ≤ 2 层；动作型操作使用子资源或明确动词端点（如 `POST /channels/{id}/join`）。
- 状态码语义严格：`200` 成功、`201` 已创建、`204` 无内容、`400` 参数错误、`401` 未认证、`403` 无权限、`404` 不存在、`409` 冲突、`422` 业务校验失败、`429` 限流、`500` 服务端错误。
- 统一错误结构：

```json
{
  "error": {
    "code": "CHANNEL_NOT_FOUND",
    "message": "频道不存在",
    "details": [],
    "requestId": "req_01H..."
  }
}
```

- 错误码是**稳定契约**：只增不改，枚举统一维护；禁止把内部异常信息直接返回给客户端。
- 分页：列表默认 `limit` ≤ 100；**消息流、动态流必须使用游标分页**，返回 `nextCursor`；偏移分页只用于后台管理类小数据量场景。
- 过滤 / 排序 / 搜索：使用 query 参数并做**白名单校验**；禁止把用户输入拼入排序字段或 SQL。
- 幂等：`POST` 创建支持 `Idempotency-Key`；更新使用版本号 / `If-Match` 防覆盖。
- 限流：按用户、IP、端点维度限流，超限返回 `429` + `Retry-After`。
- 兼容性：只增不改删；废弃字段先标记 `deprecated` 并保留至少一个版本周期。
- 契约先行：先更新 OpenAPI 契约，再实现代码；PR 中同步提交契约变更。
- ID 对外使用 UUID / ULID 等不可猜测标识；自增 ID 仅内部使用。
- 时间统一 ISO 8601 UTC（如 `2026-11-14T01:15:37Z`）。

## 8. 数据库与数据迁移

### 8.1 建模约定

- 表、列、索引统一 `snake_case`；表名复数（`channels`、`channel_members`）。
- 每张表必须有主键；业务表必须有 `created_at`、`updated_at`。
- 软删除使用 `deleted_at`（可空），并配合部分唯一索引；查询默认过滤已删除数据。
- 外键、唯一约束、索引**显式命名**，便于迁移与诊断。
- 枚举值用受控字典或约束，禁止散落魔法字符串。
- 索引必须对应真实查询场景，并在迁移说明中写清"为哪个查询服务"。

### 8.2 迁移规范

- 迁移文件**只追加、不修改历史**；命名 `YYYYMMDDHHMMSS_<描述>`。
- 破坏性变更采用**两阶段**：新增列/双写 → 回填数据 → 切换读 → 删除旧列（每阶段独立 PR）。
- 大表变更必须评估锁表时间与执行耗时；生产大表禁止长时间锁表。
- 每次迁移必须提供回滚/补偿方案并在评审中确认。
- 生产迁移前必须在预发环境演练；迁移与代码发布顺序在发布清单中写明。
- 禁止在应用代码中拼接 SQL；一律参数化查询。
- 备份与恢复演练【应当】至少每月验证一次"可恢复"，而不只是"有备份"。

## 9. 安全与隐私

### 9.1 认证与授权

- 认证：短期访问令牌（≤ 15 分钟）+ 可撤销的刷新令牌；Cookie 使用 `HttpOnly` + `Secure` + `SameSite`。
- 授权：**服务端逐资源校验**，防 IDOR 越权；权限矩阵文档化（写入 `docs/07-安全与合规.md`）并有测试覆盖。
- 敏感操作（改密码、绑手机、注销、管理端操作）要求二次确认或重新认证。
- 登录防爆破：限流 + 失败计数 + 必要时锁定或验证码。

### 9.2 数据安全

- 密码：Argon2id 或 bcrypt（cost ≥ 12）；禁止明文、MD5、SHA1。
- 密钥、令牌、连接串：只放环境变量 / 密钥管理服务；`.env` 不入库，维护 `.env.example`。
- 传输：全站 HTTPS + HSTS。
- 敏感数据（手机号、邮箱、私信内容）按需加密或脱敏存储；日志中掩码。
- 上传：校验类型、大小、内容；重命名存储；防路径穿越；必要时做恶意文件扫描。
- 数据最小化：只采集业务必需字段；支持导出与删除（注销）。

### 9.3 应用安全

- 输入：白名单 schema 校验；输出：按上下文转义（HTML/URL/JS/SQL）。
- 富文本必须走白名单净化（sanitize），禁止直接渲染用户 HTML。
- CSRF：按架构选择 token 或 SameSite 策略；CORS 白名单，禁止 `*` 携带凭证。
- 依赖与镜像：CI 每次安全扫描；高危漏洞 7 天内修复；锁定版本并提交锁文件。
- 日志脱敏：手机号、邮箱、令牌、密码、身份证等一律掩码；禁止记录完整 token。
- 安全事件响应：漏洞按 P0 处理，修复前不公开细节。

### 9.4 内容安全与社区治理（UGC 平台专项）

- 用户生成内容（频道、帖子、消息、评论、资料）必须有举报入口与处置流程。
- 敏感内容策略（词库、图片/链接检测、人工审核队列）由产品与运营确定，技术上必须可插拔。
- 封禁 / 禁言 / 删除必须留审计记录，可申诉、可追溯。
- 未成年人保护、隐私政策、用户协议在上线前完成法务确认。

## 10. 实时通信规范（若采用）

- 协议：WebSocket + JSON（或 SSE）；消息包含 `id`、`type`、`ts`、`version` 字段，便于演进与兼容。
- 连接：握手阶段鉴权；心跳间隔 30s；断线重连采用指数退避 + 抖动；重连后按游标补拉缺失消息。
- 消息：客户端生成 `clientMessageId` 用于去重；服务端保证**单频道内有序**（seq），跨频道不承诺顺序。
- 背压：每连接发送队列有上限，超限断开或降级；禁止无界缓冲。
- 单条消息载荷上限（默认 16 KB，可配置），超限拒绝并返回明确错误。
- 在线状态、typing 等瞬态事件可丢弃、不落库。
- 消息持久化与推送分离：先落库再推送，推送失败不丢数据（客户端补拉兜底）。

## 11. 性能与容量

- 性能预算（架构确认后校准）：
  - 读 API p95 ≤ 200 ms；写 API p95 ≤ 300 ms（服务端耗时，不含网络）。
  - 首屏 LCP ≤ 2.5 s；首屏 JS gzip ≤ 300 KB。
- 禁止无界列表；列表必须分页或虚拟化。
- 缓存：读多写少才缓存；明确 TTL 与失效策略；热点 key 防击穿（单飞 / 互斥）。
- 慢查询阈值 200 ms，超标必须优化或登记技术债。
- 压测：核心链路每个大版本前压测，记录基线并对比回归。
- 图片：上传即转码多尺寸 + 现代格式（WebP/AVIF），经 CDN 分发。
- 容量评估：新增功能需估算存储增长、带宽增长与峰值并发，写入设计文档。

## 12. 可观测性

- 结构化日志（JSON），字段统一：`timestamp`、`level`、`service`、`env`、`traceId`、`requestId`、`userId`（脱敏）、`route`、`status`、`durationMs`、`errorCode`。
- 日志级别：`ERROR`（需人工处理）、`WARN`（可自愈异常）、`INFO`（关键业务事件）、`DEBUG`（仅开发环境）。
- 指标：请求量 / 错误率 / 延迟（RED 方法）；资源利用率（USE 方法）；业务指标（注册、发帖、在线数、消息量）。
- 追踪：HTTP、数据库、跨服务调用透传 `traceId`；跨服务调用必须携带。
- 告警：只对"需要人采取行动"的指标告警；每条告警必须附带 runbook 链接。
- 健康检查：`/health/live`（存活）与 `/health/ready`（就绪）分离。
- 每个发布版本必须能在 5 分钟内回答："现在是否正常？哪里不正常？"

## 13. 配置与环境

- 遵循 12-Factor：配置外置；同一构建产物部署到多环境。
- 环境：`local` / `test` / `staging` / `prod`；`staging` 尽量贴近 `prod`。
- 配置在启动时校验，缺失或非法立即失败（fail fast）。
- 高风险功能必须有功能开关（feature flag），可远程关闭。
- 新增配置变量必须同步更新 `.env.example` 与部署文档。
- 禁止把环境相关逻辑写死在代码里（域名、端口、密钥、第三方地址）。

## 14. 依赖管理

- 锁文件必须提交；CI 使用锁文件安装（禁止浮动版本）。
- 新增依赖评审：维护活跃度、许可证、体积、安全记录、是否有标准库替代。
- 许可证优先 MIT / Apache-2.0 / BSD；GPL / AGPL 系需负责人批准。
- 升级节奏：每月一次常规升级窗口；安全补丁 7 天内升级。
- 禁止引入与现有能力重复的库；移除无使用依赖。

## 15. CI/CD 与发布

### 15.1 流水线（必须按序通过）

`安装依赖 → 格式检查 → Lint → 类型检查 → 单元测试 → 构建 → 集成测试 → 安全扫描 → 部署`

- `main` 绿即进入部署候选；生产发布按项目规模决定是否人工确认。
- 流水线失败必须修复，禁止跳过检查合并（临时跳过需负责人批准并登记补做）。

### 15.2 发布流程

- 发布前完成 [发布检查清单](templates/发布检查清单.md)：迁移可回滚、功能开关就绪、监控看板、回滚命令、通知。
- 小步发布；高风险变更采用灰度 / canary；异常立即回滚（代码与数据分开回滚）。
- 版本号遵循 SemVer；`CHANGELOG.md` 遵循 Keep a Changelog。
- 发布后观察 30 分钟核心指标（错误率、延迟、关键业务量），记录发布日志。
- 发布窗口与冻结期由负责人设定；冻结期内只允许紧急修复。

## 16. 缺陷与技术债管理

### 16.1 缺陷优先级

| 级别 | 定义 | 响应时限 |
| --- | --- | --- |
| P0 | 线上不可用、数据泄露、资损、严重安全问题 | 立即响应，2 小时内止血 |
| P1 | 核心功能不可用或严重降级 | 24 小时内修复 |
| P2 | 非核心功能异常、明显体验问题 | 本迭代内修复 |
| P3 | 轻微问题、优化建议 | 排期处理 |

- 缺陷流程：复现 → 分级 → 修复 + 回归测试 → 关闭；P0/P1 必须复盘并记录根因与改进项。

### 16.2 技术债

- 技术债必须登记 issue 并打 `tech-debt` 标签，写明产生原因与偿还方式。
- 每个迭代预留 10%–20% 容量偿还技术债。
- 禁止在 bugfix 中夹带大重构；重构单独提 PR。
- 临时方案（hack）必须标注 `HACK` 注释 + issue 编号 + 预计移除时间。

## 17. 文档驱动开发

- 流程：需求文档（`docs/03`）→ 架构/设计（`docs/02`、技术设计模板）→ API 契约（OpenAPI）→ 代码 → 测试 → 发布记录。
- 重大技术决策必须写 ADR（背景 / 备选方案 / 决策 / 后果），不允许只存在于聊天记录。
- PR 的完成定义（DoD）包含文档更新检查，详见 [文档体系与维护规范](01-文档体系与维护规范.md)。
- 文档与代码同仓库、同 PR 更新；禁止"代码先行、文档后补"越过评审。

## 18. AI 辅助开发约定

> 本项目允许使用 AI 辅助编码。AI 产出与人工代码**同等标准**。

- AI 生成的代码必须通过同等 CI 与评审，不得因其来源降低标准。
- 禁止"声称完成"：完成 = 代码提交 + 测试通过 + 文档更新 + 自检清单通过 + 可复现验证。
- 每次任务开始先阅读相关文档；架构或技术选型上的不确定决策先写 ADR 草案，而非悄悄选择。
- 禁止 AI 静默删除或绕过测试、修改 CI 阈值、注释掉失败用例以求通过。
- 生成的大段代码或关键安全逻辑必须人工终审。
- AI 会话中的临时结论不构成决策；需要沉淀的结论写入文档或 ADR。

## 19. 规范变更

- 本规范由项目负责人维护；修改走 PR + 版本号 + `CHANGELOG.md`。
- 每季度回顾一次规范：删除无法执行的条目，补充真实痛点；规范必须可落地、可检查。
- 规范与代码冲突时，先修正代码或先修订规范，不允许长期"双标"。
